**Process knowledge:** Load the `brainstorming` skill for detailed question techniques, approach exploration patterns, and YAGNI principles.

## Execution Flow

### Phase 0: Assess Requirements Clarity

Evaluate whether brainstorming is needed based on the feature description.

**Clear requirements indicators:**
- Specific acceptance criteria provided
- Referenced existing patterns to follow
- Described exact expected behavior
- Constrained, well-defined scope

**If requirements are already clear:**
Use **AskUserQuestion tool** to suggest: "Your requirements seem detailed enough to proceed directly to planning. Should I run `/ce:plan` instead, or would you like to explore the idea further?"

### Phase 1: Understand the Idea

#### 1.1 Repository Research (Lightweight)

Run a quick repo scan to understand existing patterns:

- Task repo-research-analyst("Understand existing patterns related to: <feature_description>")

Focus on: similar features, established patterns, CLAUDE.md guidance.

#### 1.2 Collaborative Dialogue

Use the **AskUserQuestion tool** to ask questions **one at a time**.

**Guidelines (see `brainstorming` skill for detailed techniques):**
- Prefer multiple choice when natural options exist
- Start broad (purpose, users) then narrow (constraints, edge cases)
- Validate assumptions explicitly
- Ask about success criteria

**Exit condition:** Continue until the idea is clear OR user says "proceed"

### Phase 2: Explore Approaches

Propose **2-3 concrete approaches** based on research and conversation.

For each approach, provide:
- Brief description (2-3 sentences)
- Pros and cons
- When it's best suited

Lead with your recommendation and explain why. Apply YAGNI—prefer simpler solutions.

Use **AskUserQuestion tool** to ask which approach the user prefers.

### Phase 3: Capture the Design

Write a brainstorm document to `docs/brainstorms/YYYY-MM-DD-<topic>-brainstorm.md`.

**Document structure:** See the `brainstorming` skill for the template format. Key sections: What We're Building, Why This Approach, Key Decisions, Open Questions.

Ensure `docs/brainstorms/` directory exists before writing.

**IMPORTANT:** Before proceeding to Phase 4, check if there are any Open Questions listed in the brainstorm document. If there are open questions, YOU MUST ask the user about each one using AskUserQuestion before offering to proceed to planning. Move resolved questions to a "Resolved Questions" section.

### Phase 4: Handoff

Use **AskUserQuestion tool** to present next steps:

**Question:** "Brainstorm captured. What would you like to do next?"

**Options:**
1. **Review and refine** - Improve the document through structured self-review
2. **Proceed to planning** - Run `/ce:plan` (will auto-detect this brainstorm)
3. **Share to Proof** - Upload to Proof for collaborative review and sharing
4. **Ask more questions** - I have more questions to clarify before moving on
5. **Done for now** - Return later

**If user selects "Share to Proof":**

```bash
CONTENT=$(cat docs/brainstorms/YYYY-MM-DD-<topic>-brainstorm.md)
TITLE="Brainstorm: <topic title>"
RESPONSE=$(curl -s -X POST https://www.proofeditor.ai/share/markdown \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg title "$TITLE" --arg markdown "$CONTENT" --arg by "ai:compound" '{title: $title, markdown: $markdown, by: $by}')")
PROOF_URL=$(echo "$RESPONSE" | jq -r '.tokenUrl')
```

Display the URL prominently: `View & collaborate in Proof: <PROOF_URL>`

If the curl fails, skip silently. Then return to the Phase 4 options.

**If user selects "Ask more questions":** YOU (Claude) return to Phase 1.2 (Collaborative Dialogue) and continue asking the USER questions one at a time to further refine the design. The user wants YOU to probe deeper - ask about edge cases, constraints, preferences, or areas not yet explored. Continue until the user is satisfied, then return to Phase 4.

**If user selects "Review and refine":**

Load the `document-review` skill and apply it to the brainstorm document.

When document-review returns "Review complete", present next steps:

1. **Move to planning** - Continue to `/ce:plan` with this document
2. **Done for now** - Brainstorming complete. To start planning later: `/ce:plan [document-path]`

## Output Summary

When complete, display:

```
Brainstorm complete!

Document: docs/brainstorms/YYYY-MM-DD-<topic>-brainstorm.md

Key decisions:
- [Decision 1]
- [Decision 2]

Next: Run `/ce:plan` when ready to implement.
```

## Important Guidelines

- **Stay focused on WHAT, not HOW** - Implementation details belong in the plan
- **Ask one question at a time** - Don't overwhelm
- **Apply YAGNI** - Prefer simpler approaches
- **Keep outputs concise** - 200-300 words per section max

NEVER CODE! Just explore and document decisions.

# Create a plan for a new feature or bug fix

## Introduction

**Note: The current year is 2026.** Use this when dating plans and searching for recent documentation.

Transform feature descriptions, bug reports, or improvement ideas into well-structured markdown files issues that follow project conventions and best practices. This command provides flexible detail levels to match your needs.

## Feature Description

<feature_description> #docs/brainstorms/2026-03-12-dashboard-improvements-brainstorm.md </feature_description>

**If the feature description above is empty, ask the user:** "What would you like to plan? Please describe the feature, bug fix, or improvement you have in mind."

Do not proceed until you have a clear feature description from the user.

### 0. Idea Refinement

**Check for brainstorm output first:**

Before asking questions, look for recent brainstorm documents in `docs/brainstorms/` that match this feature:

```bash
ls -la docs/brainstorms/*.md 2>/dev/null | head -10
```

**Relevance criteria:** A brainstorm is relevant if:
- The topic (from filename or YAML frontmatter) semantically matches the feature description
- Created within the last 14 days
- If multiple candidates match, use the most recent one

**If a relevant brainstorm exists:**
1. Read the brainstorm document **thoroughly** — every section matters
2. Announce: "Found brainstorm from [date]: [topic]. Using as foundation for planning."
3. Extract and carry forward **ALL** of the following into the plan:
   - Key decisions and their rationale
   - Chosen approach and why alternatives were rejected
   - Constraints and requirements discovered during brainstorming
   - Open questions (flag these for resolution during planning)
   - Success criteria and scope boundaries
   - Any specific technical choices or patterns discussed
4. **Skip the idea refinement questions below** — the brainstorm already answered WHAT to build
5. Use brainstorm content as the **primary input** to research and planning phases
6. **Critical: The brainstorm is the origin document.** Throughout the plan, reference specific decisions with `(see brainstorm: docs/brainstorms/<filename>)` when carrying forward conclusions. Do not paraphrase decisions in a way that loses their original context — link back to the source.
7. **Do not omit brainstorm content** — if the brainstorm discussed it, the plan must address it (even if briefly). Scan each brainstorm section before finalizing the plan to verify nothing was dropped.

**If multiple brainstorms could match:**
Use **AskUserQuestion tool** to ask which brainstorm to use, or whether to proceed without one.

**If no brainstorm found (or not relevant), run idea refinement:**

Refine the idea through collaborative dialogue using the **AskUserQuestion tool**:

- Ask questions one at a time to understand the idea fully
- Prefer multiple choice questions when natural options exist
- Focus on understanding: purpose, constraints and success criteria
- Continue until the idea is clear OR user says "proceed"

**Gather signals for research decision.** During refinement, note:

- **User's familiarity**: Do they know the codebase patterns? Are they pointing to examples?
- **User's intent**: Speed vs thoroughness? Exploration vs execution?
- **Topic risk**: Security, payments, external APIs warrant more caution
- **Uncertainty level**: Is the approach clear or open-ended?

**Skip option:** If the feature description is already detailed, offer:
"Your description is clear. Should I proceed with research, or would you like to refine it further?"

## Main Tasks

### 1. Local Research (Always Runs - Parallel)

<thinking>
First, I need to understand the project's conventions, existing patterns, and any documented learnings. This is fast and local - it informs whether external research is needed.
</thinking>

Run these agents **in parallel** to gather local context:

- Task repo-research-analyst(feature_description)
- Task learnings-researcher(feature_description)

**What to look for:**
- **Repo research:** existing patterns, CLAUDE.md guidance, technology familiarity, pattern consistency
- **Learnings:** documented solutions in `docs/solutions/` that might apply (gotchas, patterns, lessons learned)

These findings inform the next step.

### 1.5. Research Decision

Based on signals from Step 0 and findings from Step 1, decide on external research.

**High-risk topics → always research.** Security, payments, external APIs, data privacy. The cost of missing something is too high. This takes precedence over speed signals.

**Strong local context → skip external research.** Codebase has good patterns, CLAUDE.md has guidance, user knows what they want. External research adds little value.

**Uncertainty or unfamiliar territory → research.** User is exploring, codebase has no examples, new technology. External perspective is valuable.

**Announce the decision and proceed.** Brief explanation, then continue. User can redirect if needed.

Examples:
- "Your codebase has solid patterns for this. Proceeding without external research."
- "This involves payment processing, so I'll research current best practices first."

### 1.5b. External Research (Conditional)

**Only run if Step 1.5 indicates external research is valuable.**

Run these agents in parallel:

- Task best-practices-researcher(feature_description)
- Task framework-docs-researcher(feature_description)

### 1.6. Consolidate Research

After all research steps complete, consolidate findings:

- Document relevant file paths from repo research (e.g., `app/services/example_service.rb:42`)
- **Include relevant institutional learnings** from `docs/solutions/` (key insights, gotchas to avoid)
- Note external documentation URLs and best practices (if external research was done)
- List related issues or PRs discovered
- Capture CLAUDE.md conventions

**Optional validation:** Briefly summarize findings and ask if anything looks off or missing before proceeding to planning.

# Deepen Plan - Power Enhancement Mode

## Introduction

**Note: The current year is 2026.** Use this when searching for recent documentation and best practices.

This command takes an existing plan (from `/ce:plan`) and enhances each section with parallel research agents. Each major element gets its own dedicated research sub-agent to find:
- Best practices and industry patterns
- Performance optimizations
- UI/UX improvements (if applicable)
- Quality enhancements and edge cases
- Real-world implementation examples

The result is a deeply grounded, production-ready plan with concrete implementation details.

## Plan File

<plan_path> #docs/plans/2026-03-12-feat-dashboard-overhaul-plan.md </plan_path>

## Dash AG Grid v31.2.0 Best Practices Research

### 1. Multi-Row Selection with Checkboxes

In v31, checkbox selection moved from `columnDefs` to `dashGridOptions`. The old `checkboxSelection` and `headerCheckboxSelection` column properties are **deprecated**.

**Correct v31 pattern:**

```python
dag.AgGrid(
    id="my-grid",
    rowData=df.to_dict("records"),
    columnDefs=[
        {"field": "date", "headerName": "Date"},
        {"field": "model", "headerName": "Model"},
        # No checkboxSelection here in v31!
    ],
    dashGridOptions={
        "rowSelection": {
            "mode": "multiRow",
            "checkboxes": True,           # default True for multiRow
            "headerCheckbox": True,        # default True for multiRow
            "selectAll": "filtered",       # or "all" or "currentPage"
            "enableClickSelection": True,  # click row to select (not just checkbox)
        },
        "pagination": True,
        "paginationPageSize": 100,
    },
)
```

**Interaction with pagination:** Use `"selectAll": "currentPage"` to limit header-checkbox "select all" to the visible page. Use `"selectAll": "all"` (default) to select across all pages. Use `"selectAll": "filtered"` to select all rows matching the current filter.

### 2. Programmatically Setting selectedRows from a Callback

The `selectedRows` property supports **three forms** as an Output:

```python
# Form 1: Pass row data objects (if getRowId is defined, only the ID fields are needed)
@callback(
    Output("my-grid", "selectedRows"),
    Input("url", "search"),
)
def restore_selection(search):
    selected_ids = parse_ids_from_url(search)
    # Return list of dicts with at least the fields used by getRowId
    return [{"run_id": rid} for rid in selected_ids]

# Form 2: Pass row IDs directly
def restore_selection(search):
    selected_ids = parse_ids_from_url(search)
    return {"ids": selected_ids}  # list of string IDs

# Form 3: Pass a JS function string
def restore_selection(search):
    return {"function": "params.data.status === 'completed'"}
```

**Important:** You should define `getRowId` on the grid for reliable ID-based selection:

```python
dag.AgGrid(
    # ...
    getRowId="params.data.run_id",  # JS expression returning unique ID
)
```

The `{"ids": [...]}` form is the cleanest for restoring selection from URL state.

### 3. selectedRows with Client-Side Pagination (500 Rows)

For 500 rows with client-side data, you are using the **Client-Side Row Model** (the default), not SSRM. This is important because:

- Client-side pagination works correctly with `selectAll: "currentPage"`, `"filtered"`, and `"all"`.
- The **Server-Side Row Model (SSRM)** has a known limitation where `selectAll: "currentPage"` and `"filtered"` are ignored and treated as `"all"`.
- With client-side data, all 500 rows are already in the browser -- pagination is purely visual.

**Recommended configuration:**

```python
dag.AgGrid(
    rowData=df.to_dict("records"),  # all 500 rows
    columnDefs=column_defs,
    getRowId="params.data.run_id",
    dashGridOptions={
        "rowSelection": {
            "mode": "multiRow",
            "checkboxes": True,
            "headerCheckbox": True,
            "selectAll": "filtered",  # header checkbox selects all filtered rows across pages
        },
        "pagination": True,
        "paginationPageSize": 100,
        "paginationPageSizeSelector": [50, 100, 200, 500],
    },
)
```

When reading `selectedRows` as an Input, it returns the full row data for all selected rows (across all pages), not just the current page.

### 4. Default Sorting on Multiple Columns

Use `sort` and `sortIndex` in `columnDefs`. The `sortIndex` controls the priority when multiple columns are sorted:

```python
columnDefs = [
    {
        "field": "date",
        "headerName": "Date",
        "sort": "desc",
        "sortIndex": 0,        # primary sort
    },
    {
        "field": "model",
        "headerName": "Model",
        "sort": "asc",
        "sortIndex": 1,        # secondary sort
    },
    {
        "field": "context_length",
        "headerName": "Context",
        "sort": "asc",
        "sortIndex": 2,        # tertiary sort
    },
    {"field": "score", "headerName": "Score"},
    # ...
]
```

**Note on `initialSort`:** There is also `initialSort` (and `initialSortIndex`) which only applies when columns are first created and won't be re-applied if columnDefs are updated. Use `sort`/`sortIndex` for the stateful version that persists across columnDef updates.

### 5. Column Visibility Toggling via Callback

Use the `columnState` property (not `columnDefs` updates) for toggling visibility:

```python
dag.AgGrid(
    id="my-grid",
    columnDefs=column_defs,
    # ...
)

@callback(
    Output("my-grid", "columnState"),
    Input("toggle-columns-checklist", "value"),  # list of visible column IDs
    State("my-grid", "columnState"),
)
def toggle_columns(visible_cols, current_state):
    if not current_state:
        return no_update
    new_state = []
    for col in current_state:
        col_copy = dict(col)
        col_copy["hide"] = col_copy["colId"] not in visible_cols
        new_state.append(col_copy)
    return new_state
```

**Key point:** `columnState` is both an Input (to read current state) and an Output (to set state). Each entry has `colId`, `hide`, `width`, `sort`, `sortIndex`, `pinned`, etc.

### 6. Hidden-by-Default Columns (e.g., File Paths)

Use `hide: True` in `columnDefs`:

```python
columnDefs = [
    {"field": "run_id", "headerName": "Run ID"},
    {"field": "model", "headerName": "Model"},
    # Hidden by default -- user can toggle via sidebar or callback
    {
        "field": "results_path",
        "headerName": "Results Path",
        "hide": True,
    },
    {
        "field": "config_path",
        "headerName": "Config Path",
        "hide": True,
    },
]
```

If you want to use the **initial** (non-stateful) variant: use `initialHide: True` instead. The difference: `hide` is stateful and will be re-applied if you update `columnDefs`; `initialHide` only applies on column creation.

To also hide the column from the AG Grid sidebar/tool panel, add `"suppressColumnsToolPanel": True`.

### 7. Performance with 500 Rows and Multi-Select

**No known issues.** 500 rows is well within the comfort zone for AG Grid's client-side row model. AG Grid is designed to handle tens of thousands of rows with virtual scrolling. At 500 rows:

- All data is in the browser (client-side model).
- Pagination at 100 rows/page means only 100 DOM nodes rendered at a time.
- Multi-select with checkboxes adds negligible overhead.
- `selectedRows` callbacks fire with the full selected row data, which at 500 rows max is trivial.

**One thing to watch:** If your row data contains very large fields (e.g., long file paths or embedded JSON), it can slow down the callback serialization. Keep `rowData` lean -- only include fields you actually display or need for selection/filtering.

```python
    {"field": "score", "headerName": "Score"},
    {"field": "status", "headerName": "Status"},
    # Hidden columns

    {"field": "config_path", "headerName": "Config Path", "hide": True},
]

app.layout = html.Div([
    dag.AgGrid(
        id="results-grid",
        columnDefs=column_defs,
        rowData=[],  # populated by callback
        getRowId="params.data.run_id",
        dashGridOptions={
            "rowSelection": {
                "mode": "multiRow",
                "checkboxes": True,
                "headerCheckbox": True,
                "selectAll": "filtered",
                "enableClickSelection": True,
            },
            "pagination": True,
            "paginationPageSize": 100,
            "paginationPageSizeSelector": [50, 100, 200, 500],
            "animateRows": False,
        },
        defaultColDef={
            "sortable": True,
            "filter": True,
            "resizable": True,
        },
        style={"height": "70vh"},
    ),
])

# Restore selection from URL
@callback(
    Output("results-grid", "selectedRows"),
    Input("url", "search"),
)
def restore_selection(search):
    if not search:
        return no_update
    ids = parse_ids(search)
    return {"ids": ids}

# Toggle column visibility
@callback(
    Output("results-grid", "columnState"),
    Input("column-toggle", "value"),
    State("results-grid", "columnState"),
)
def toggle_columns(visible, state):
    if not state:
        return no_update
    return [
        {**col, "hide": col["colId"] not in visible}
        for col in state
    ]
```

## Dash 2.18 URL State Synchronization: Patterns and Recommendations

### 1. Preventing Circular Callback Loops (dcc.Location <-> dcc.Store)

The fundamental problem: if callback A writes to `dcc.Location` when stores change, and callback B writes to stores when `dcc.Location` changes, you get an infinite loop.

**Recommended pattern: use `ctx.triggered_id` to break the cycle.**

```python
from dash import callback_context as ctx, no_update
from urllib.parse import urlencode, parse_qs

@app.callback(
    # Outputs: both the URL and the stores
    Output("url", "search"),
    Output("selected-run-id", "data"),
    Output("tabs", "active_tab"),
    # Inputs: both the URL and the UI controls
    Input("url", "search"),           # URL changed (browser nav, manual edit)
    Input("trace-run-selector", "value"),  # UI control changed
    Input("tabs", "active_tab"),
    # States for reading current values without triggering
    State("selected-run-id", "data"),
    prevent_initial_call=False,
)
def sync_url_and_state(url_search, selected_run, active_tab, current_run_store):
    triggered = ctx.triggered_id  # Dash 2.x: returns the component id string

    if triggered == "url":
        # URL changed → parse and push to stores, DON'T update URL back
        params = parse_qs(url_search.lstrip("?")) if url_search else {}
        run_id = params.get("run", [None])[0]
        tab = params.get("tab", ["overview"])[0]
        return no_update, run_id, tab

    elif triggered in ("trace-run-selector", "tabs"):
        # UI changed → update URL, DON'T update stores (they already have the value)
        params = {}
        if selected_run:
            params["run"] = selected_run
        if active_tab:
            params["tab"] = active_tab
        new_search = f"?{urlencode(params)}" if params else ""
        return new_search, no_update, no_update

    # Initial load: read from URL
    if url_search:
        params = parse_qs(url_search.lstrip("?"))
        run_id = params.get("run", [None])[0]
        tab = params.get("tab", ["overview"])[0]
        return no_update, run_id, tab

    return no_update, no_update, no_update
```

**Key insight:** `no_update` is the cycle-breaker. When the URL triggers the callback, you update stores but return `no_update` for the URL output. When a UI control triggers, you update the URL but return `no_update` for the stores.

### 2. Single Callback vs. Two Callbacks

**A single callback is better** for exactly this reason -- it can inspect `ctx.triggered_id` and decide which direction to sync. Two separate callbacks inherently create a cycle unless you add extra guards (hidden flags, intermediate stores), which adds complexity.

However, there is a practical limit: if you have many UI controls that should update the URL, the single callback's Input list gets long. The solution is to **use a single intermediate `dcc.Store` as the "state bundle"** and have two callbacks:

```python
# Pattern: State Bundle Store
# Many UI controls → one "state-bundle" store → URL sync

# Callback 1: UI controls update the bundle (no URL involvement)
@app.callback(
    Output("state-bundle", "data"),
    Input("trace-run-selector", "value"),
    Input("tabs", "active_tab"),
    Input("date-range", "start_date"),
    Input("date-range", "end_date"),
    Input("filter-dropdown", "value"),
    State("state-bundle", "data"),
    prevent_initial_call=True,
)
def ui_to_bundle(run_id, tab, start, end, filters, current_bundle):
    bundle = current_bundle or {}
    # Only update the key that actually changed
    trigger = ctx.triggered_id
    if trigger == "trace-run-selector":
        bundle["run"] = run_id
    elif trigger == "tabs":
        bundle["tab"] = tab
    elif trigger == "date-range":
        bundle["start"] = start
        bundle["end"] = end
    elif trigger == "filter-dropdown":
        bundle["filters"] = filters
    return bundle

# Callback 2: Bidirectional sync between bundle and URL
@app.callback(
    Output("url", "search"),
    Output("state-bundle", "data", allow_duplicate=True),
    Input("url", "search"),
    Input("state-bundle", "data"),
    prevent_initial_call=True,
)
def sync_bundle_url(url_search, bundle):
    trigger = ctx.triggered_id
    if trigger == "url":
        # URL → bundle
        params = parse_qs(url_search.lstrip("?")) if url_search else {}
        new_bundle = {k: v[0] if len(v) == 1 else v for k, v in params.items()}
        return no_update, new_bundle
    elif trigger == "state-bundle":
        # Bundle → URL
        params = {k: v for k, v in (bundle or {}).items() if v is not None}
        return f"?{urlencode(params, doseq=True)}" if params else "", no_update
    return no_update, no_update
```

This is cleaner because the URL sync logic is isolated from the many UI controls.

### 3. Handling Long URL Query Params (50+ Run IDs)

URLs have practical limits (~2000 chars in older browsers, ~8000 in modern ones, but proxies/servers may truncate). With 50+ 8-char hex run IDs:

```
?runs=a1b2c3d4,e5f6g7h8,...  # 50 IDs x ~9 chars = ~450 chars. Fine.
```

50 run IDs at 8 chars + comma = ~450 characters. That's well within limits. But if it grows to hundreds:

**Strategy A: Compress with base64-encoded JSON (if really needed)**
```python
import base64, json, zlib

def encode_state(state_dict):
    """Compress state for URL."""
    raw = json.dumps(state_dict, separators=(",", ":")).encode()
    compressed = base64.urlsafe_b64encode(zlib.compress(raw)).decode()
    return compressed

def decode_state(encoded):
    raw = zlib.decompress(base64.urlsafe_b64decode(encoded))
    return json.loads(raw)

# URL: ?s=eJzLKM3JyVcozy_K...
```

**Strategy B (recommended for your case): Use `dcc.Location` hash instead of search**
```python
# Store bulky state in hash fragment (never sent to server)
# ?tab=trace&start=2026-01-01#runs=a1b2c3d4,e5f6g7h8,...
```

**Strategy C: Only store "selection name" in URL, not all IDs**
If the user selects runs by experiment name or filter criteria, store the filter in the URL rather than the expanded list of IDs:
```
?experiment=dou2020_gdc&model=gpt-4o  # Instead of listing all matching run IDs
```

For your dashboard with 8-char hex IDs, comma-separated in the query string is fine up to ~200 IDs before you'd need to worry.

### 4. dcc.Location: refresh, pathname vs search vs hash

```python
dcc.Location(id="url", refresh=False)  # ALWAYS use refresh=False for SPA state sync
```

| Property | When to use | Server sees it? | Triggers page reload? |
|----------|-------------|-----------------|----------------------|
| `pathname` | Tab/page routing (`/overview`, `/trace/abc123`) | Yes | Only if `refresh=True` |
| `search` | Filters, selections (`?tab=trace&run=abc123`) | Yes | Only if `refresh=True` |
| `hash` | Bulky state, client-only state (`#runs=a,b,c`) | No | Never |

**For your dashboard:**
- Use `search` for the primary state (active tab, selected run, date range). This makes URLs shareable and bookmarkable.
- Use `hash` only if you have state too bulky for the query string.
- `refresh=False` is mandatory -- without it, every state change reloads the page and kills the SPA experience.
- `pathname` is useful if you want clean routes like `/trace/abc123` instead of `?tab=trace&run=abc123`, but it requires `dcc.Location` + page routing logic and is more work for marginal benefit in a single-page dashboard.

### 7. Gotchas

1. **Initial page load:** `ctx.triggered` is an empty list on initial load. Handle this explicitly -- typically you want to read from URL on first load.

2. **`refresh=False` + `search` updates:** When you write to `dcc.Location.search`, Dash updates the browser URL bar via `pushState` without a page reload. However, each write creates a browser history entry. Rapid filter changes can pollute the back button. Consider using `hash` for volatile state or debouncing URL updates with a small `dcc.Interval`.

3. **`prevent_initial_call=False` is needed** for the URL sync callback so it runs on page load and reads initial URL params.

4. **`parse_qs` returns lists:** `parse_qs("?tab=trace")` gives `{"tab": ["trace"]}`, not `{"tab": "trace"}`. Always index `[0]`.

5. **Empty `search` string:** `dcc.Location.search` can be `""` or `None` on initial load depending on whether the URL has a `?`. Guard both cases.

6. **`storage_type="session"` conflict:** Your existing stores use session storage. On page load, both the URL params AND the session storage will have values. Decide which wins -- typically the URL should take precedence (it's what the user navigated to), but you may want session storage as fallback when URL has no params.</result>

## 1. Lazy Tab Rendering

The recommended Dash pattern is the **callback-based content method** -- you do NOT put content inside `dcc.Tab(children=...)`. Instead, you render content into a separate container only when the tab is selected:

```python
app.layout = html.Div([
    dcc.Tabs(id="tabs", value="tab-overview", children=[
        dcc.Tab(label="Overview", value="tab-overview"),
        dcc.Tab(label="Plots",    value="tab-plots"),
        dcc.Tab(label="Logs",     value="tab-logs"),
    ]),
    html.Div(id="tab-content"),
])

@callback(Output("tab-content", "children"), Input("tabs", "value"))
def render_tab(tab):
    if tab == "tab-overview":
        return build_overview_layout()
    elif tab == "tab-plots":
        return build_plots_layout()   # plots only built when tab is clicked
    elif tab == "tab-logs":
        return build_logs_layout()
    return html.Div()
```

Key points:
- Content for inactive tabs is **never constructed** -- the Python functions only run when the tab is selected.
- This avoids the "render all tabs upfront" problem that happens when you use `dcc.Tab(children=[dcc.Graph(...)])`.
- Do NOT wrap the entire `tab-content` div in `dcc.Loading` if your tabs contain sub-callbacks that trigger their own loading states; wrap individual heavy components instead.

## 5. Subprocess in Callbacks

**Use background callbacks with `DiskcacheManager` for subprocess calls.** This runs the callback in a separate process so the main Dash server stays responsive:

```python

import subprocess
from dash import Dash, callback, Input, Output, html, DiskcacheManager

cache = diskcache.Cache("./cache")
background_callback_manager = DiskcacheManager(cache)

app = Dash(__name__, background_callback_manager=background_callback_manager)

@callback(
    Output("cli-output", "children"),
    Input("run-analysis-btn", "n_clicks"),
    background=True,
    running=[
        (Output("run-analysis-btn", "disabled"), True, False),
        (Output("status-text", "children"), "Running analysis...", ""),
    ],
    progress=[Output("progress-bar", "value"), Output("progress-bar", "max")],
    prevent_initial_call=True,
)
def run_cli_tool(set_progress, n_clicks):
    set_progress((0, 100))
    
    result = subprocess.run(
        [".venv/bin/python", "my_cli_tool.py", "--arg", "value"],
        capture_output=True, text=True, timeout=300,
    )
    
    set_progress((100, 100))
    
    if result.returncode != 0:
        return html.Pre(f"ERROR:\n{result.stderr}", style={"color": "red"})
    return html.Pre(result.stdout)
```

Key points:
- The `running` parameter disables the button and shows status text while the callback executes.
- The `progress` parameter with `set_progress` enables progress updates.

- For real-time streaming output, use `subprocess.Popen` with line-by-line reading and call `set_progress` per line.

```python
def run_cli_tool(set_progress, n_clicks):

    )
    lines = []
    for i, line in enumerate(proc.stdout):
        lines.append(line.rstrip())
        set_progress((i, "running"))  # update progress per line
    proc.wait()
    return html.Pre("\n".join(lines))
```

**Other performance strategies:**

| Technique | When to Use |
|-----------|-------------|
| `prevent_initial_call=True` | Any callback that responds to user action (buttons, dropdowns) |
| `dcc.Store` with `storage_type="session"` | Cache computed data client-side to avoid recomputation |
| `flask_caching` / `@cache.memoize()` | Server-side caching for expensive data loads |
| Partial property updates (`Patch()`) | Update one trace/style without resending entire figure |
| Clientside callbacks | Visibility toggles, CSS changes, simple formatting |
| Lazy tab rendering (pattern #1 above) | Avoid computing all tabs on load |
| `background=True` | Any callback that takes >2-3 seconds |

**Partial property updates** (Dash 2.9+) for updating a figure without re-sending all data:

```python

          prevent_initial_call=True)

    patched["data"][0]["marker"]["color"] = color
    return patched  # only the diff is sent, not the whole figure
```

**Avoid these common pitfalls with 20+ callbacks:**
- Don't use pattern-matching callbacks with hundreds of dynamic components -- there is a known performance issue (#3008) where Dash's front-end matching becomes slow.
- Don't nest `dcc.Loading` wrappers deeply -- each one adds overhead.
- Use `orjson` serialization (built into Dash 2.x) -- it is automatic but ensure you are not overriding the JSON encoder.

It gives you a styled, accessible toggle header out of the box (no separate button needed), supports `always_open` for multiple sections, and `start_collapsed` to default-closed. `dbc.Collapse` requires you to wire up your own toggle button. `html.Details` works but looks unstyled and is harder to animate.

```python
import dash_bootstrap_components as dbc

def make_options_panel(tab_id):
    """Collapsible options panel for the top of a tab."""
    return dbc.Accordion(
        [
            dbc.AccordionItem(
                [
                    dbc.Row([
                        dbc.Col([
                            dbc.Label("Dataset"),
                            dcc.Dropdown(
                                id={"type": "dataset-dropdown", "tab": tab_id},
                                options=[],
                                placeholder="Select dataset...",
                            ),
                        ], md=4),
                        dbc.Col([
                            dbc.Label("Metric"),
                            dcc.Dropdown(
                                id={"type": "metric-dropdown", "tab": tab_id},
                                options=[
                                    {"label": "Accuracy", "value": "accuracy"},
                                    {"label": "F1 Score", "value": "f1"},
                                ],
                                value="accuracy",
                            ),
                        ], md=4),
                        dbc.Col([
                            dbc.Label("Options"),
                            dbc.Checklist(
                                id={"type": "options-checklist", "tab": tab_id},
                                options=[
                                    {"label": "Show errors", "value": "errors"},
                                    {"label": "Normalize", "value": "normalize"},
                                ],
                                value=[],
                                inline=True,
                            ),
                        ], md=4),
                    ]),
                ],
                title="Options",  # This is the clickable header text
                item_id="options",
            ),
        ],
        id={"type": "options-accordion", "tab": tab_id},
        start_collapsed=True,  # Collapsed by default
        flush=True,            # Remove outer border for cleaner embedding
        className="mb-3",

```

## 3. Multi-Filter Widget (dynamic add/remove rows)

**Recommendation: Pattern-matching callbacks with `Patch()` for partial updates.**

This uses dict-based IDs with `MATCH` and `ALL` selectors. Each filter row gets a unique index. `Patch()` (Dash 2.9+) lets you append/remove children without returning the entire children list.

```python
from dash import html, dcc, callback, Input, Output, State, ALL, MATCH, Patch, no_update, ctx
import dash_bootstrap_components as dbc

# ---------- Layout ----------

def make_filter_widget(columns):
    """Dynamic multi-filter widget. `columns` is a list of column names."""
    return html.Div([
        html.Div(id="filter-rows-container", children=[]),
        dbc.Button(
            "+ Add Filter",
            id="add-filter-btn",
            color="secondary",
            size="sm",
            className="mt-2",
        ),
        # Hidden store to track the next index (avoids ID collisions after deletion)
        dcc.Store(id="filter-next-index", data=0),
        # Store the column list so callbacks can access it
        dcc.Store(id="filter-columns", data=columns),
    ])


def make_filter_row(index, columns):
    """Create a single filter row."""
    operators = [
        {"label": "equals", "value": "eq"},
        {"label": "not equals", "value": "ne"},
        {"label": "contains", "value": "contains"},
        {"label": "starts with", "value": "startswith"},
        {"label": "is empty", "value": "empty"},
        {"label": "is not empty", "value": "notempty"},
    ]
    return dbc.Row(
        [
            dbc.Col(
                dcc.Dropdown(
                    id={"type": "filter-column", "index": index},
                    options=[{"label": c, "value": c} for c in columns],
                    placeholder="Column...",
                ),
                md=4,
            ),
            dbc.Col(
                dcc.Dropdown(
                    id={"type": "filter-operator", "index": index},
                    options=operators,
                    value="eq",
                    clearable=False,
                ),
                md=2,
            ),
            dbc.Col(
                dbc.Input(
                    id={"type": "filter-value", "index": index},
                    placeholder="Value...",
                    type="text",
                    size="sm",
                ),
                md=4,
            ),
            dbc.Col(
                dbc.Button(
                    "x",
                    id={"type": "filter-delete", "index": index},
                    color="danger",
                    outline=True,
                    size="sm",
                ),
                md=2,
            ),
        ],
        className="g-2 mb-2 align-items-center",
        id={"type": "filter-row", "index": index},
    )


# ---------- Callbacks ----------

@callback(
    Output("filter-rows-container", "children"),
    Output("filter-next-index", "data"),
    Input("add-filter-btn", "n_clicks"),
    State("filter-next-index", "data"),
    State("filter-columns", "data"),
    prevent_initial_call=True,
)
def add_filter_row(n_clicks, next_index, columns):
    """Append a new filter row using Patch (partial update)."""
    patched = Patch()
    patched.append(make_filter_row(next_index, columns))
    return patched, next_index + 1


@callback(
    Output("filter-rows-container", "children", allow_duplicate=True),
    Input({"type": "filter-delete", "index": ALL}, "n_clicks"),
    State({"type": "filter-row", "index": ALL}, "id"),
    prevent_initial_call=True,
)
def remove_filter_row(n_clicks_list, row_ids):
    """Remove the clicked filter row. Rebuilds children minus the deleted row."""
    if not ctx.triggered_id or not any(n for n in n_clicks_list if n):
        return no_update
    # ctx.triggered_id is the dict ID of the clicked delete button
    delete_index = ctx.triggered_id["index"]
    # Use Patch to remove by position
    # Find the position of the row to remove
    for pos, row_id in enumerate(row_ids):
        if row_id["index"] == delete_index:
            patched = Patch()
            del patched[pos]
            return patched
    return no_update


@callback(
    Output("current-filters-store", "data"),  # Wire this to wherever you need filters
    Input({"type": "filter-column", "index": ALL}, "value"),
    Input({"type": "filter-operator", "index": ALL}, "value"),
    Input({"type": "filter-value", "index": ALL}, "value"),
    State({"type": "filter-column", "index": ALL}, "id"),
    prevent_initial_call=True,
)
def collect_filters(columns, operators, values, ids):
    """Collect all active filters into a list of dicts."""
    filters = []
    for col, op, val, id_dict in zip(columns, operators, values, ids):
        if col is not None:
            filters.append({
                "column": col,
                "operator": op,
                "value": val or "",
                "index": id_dict["index"],
            })
    return filters
```

**Key points about pattern-matching callbacks:**
- IDs are dicts: `{"type": "filter-column", "index": 3}`.
- `ALL` fires whenever *any* component of that type changes, passing all values as a list.
- `MATCH` fires per-component and passes only the matched value (useful for row-level reactions).
- `ctx.triggered_id` (Dash 2.4+) gives you the dict ID of whichever component triggered.
- `Patch()` (Dash 2.9+) lets you do `patched.append(...)` or `del patched[i]` for partial children updates.
- `allow_duplicate=True` is needed when multiple callbacks write to the same Output.

## 4. dcc.Clipboard

**Two usage modes:** target_id-based (no callback needed) and content-based (callback-driven).

```python
from dash import html, dcc, callback, Input, Output

# --- Mode 1: target_id (simplest, no callback) ---
# Copies the inner text/value of the target element.

html.Div([
    html.Pre(
        "some-value-to-copy",
        id="copy-target",
        style={"padding": "0.5rem", "backgroundColor": "#f8f9fa"},
    ),
    dcc.Clipboard(
        target_id="copy-target",
        title="Copy to clipboard",  # Tooltip text
        style={
            "display": "inline-block",
            "fontSize": 20,
            "verticalAlign": "top",
        },
    ),
], style={"position": "relative"})


# --- Mode 2: content prop (callback-driven, for computed text) ---
# Useful when you want to copy something different from what is displayed,
# or when the source is not a simple text element.

html.Div([
    html.Div("Displayed summary info", id="summary-display"),
    dcc.Clipboard(id="copy-full-json", title="Copy full JSON"),
])

@callback(
    Output("copy-full-json", "content"),
    Input("copy-full-json", "n_clicks"),
    State("my-data-store", "data"),
    prevent_initial_call=True,
)
def set_clipboard_content(n_clicks, data):
    import json
    return json.dumps(data, indent=2)
```

**Gotchas and notes:**
- `dcc.Clipboard` renders as a small copy icon by default. You can style it or wrap it.
- `target_id` copies `.innerText` of the target; for `dcc.Input`/`dbc.Input` it copies `.value`.
- If both `target_id` and `content` are set, `content` takes precedence when populated.
- The component uses the browser Clipboard API. There is no built-in fallback -- it silently fails in insecure contexts (non-HTTPS, non-localhost). For HPC port-forwarded dashboards over SSH tunnels, localhost works fine.
- Available since Dash 2.0. No compatibility issues in 2.18.

## 5. Toast Notifications

**Recommendation: `dbc.Toast` with `duration` for auto-dismiss, positioned fixed in top-right corner.**

```python
@callback(

    # Return True for is_open to show it; duration handles auto-close.
    return True, "Saved", "success", "Configuration saved successfully."

@callback(
    Output("notification-toast", "is_open", allow_duplicate=True),
    Output("notification-toast", "header", allow_duplicate=True),
    Output("notification-toast", "icon", allow_duplicate=True),

        return True, "Success", "success", "Run completed."

        return True, "Error", "danger", f"Run failed: {e}"
```

## 6. Searchable Dropdown

`dcc.Dropdown` has `search_value` built in (search is enabled by default). The key gotcha is around custom/component labels.

```python
from dash import html, dcc

# --- Basic: string labels (search works automatically) ---
dcc.Dropdown(
    id="model-dropdown",
    options=[
        {"label": "GPT-4o (OpenAI)", "value": "openai/gpt-4o"},
        {"label": "Claude Opus 4 (Anthropic)", "value": "anthropic/claude-opus-4"},
        {"label": "Llama 3.1 70B (Meta)", "value": "meta/llama-3.1-70b"},
    ],
    placeholder="Search models...",
    searchable=True,       # This is True by default
    clearable=True,
    # optionHeight=50,     # Increase if labels are tall
)


# --- With styled component labels: MUST set `search` property ---
# Gotcha: when label is a Dash component, search matches against `value` only.
# Fix: add the `search` key to each option.

dcc.Dropdown(
    id="model-dropdown-styled",
    options=[
        {
            "label": html.Span([
                html.Span("GPT-4o", style={"fontWeight": "bold"}),
                html.Span(" - OpenAI", style={"color": "#888", "marginLeft": "0.5rem"}),
            ]),
            "value": "openai/gpt-4o",
            "search": "GPT-4o OpenAI gpt4o",  # All searchable terms
        },
        {
            "label": html.Span([
                html.Span("Claude Opus 4", style={"fontWeight": "bold"}),
                html.Span(" - Anthropic", style={"color": "#888", "marginLeft": "0.5rem"}),
            ]),
            "value": "anthropic/claude-opus-4",
            "search": "Claude Opus 4 Anthropic claude-opus-4",
        },
        {
            "label": html.Span([
                html.Span("Llama 3.1 70B", style={"fontWeight": "bold"}),
                html.Span(" - Meta", style={"color": "#888", "marginLeft": "0.5rem"}),
            ]),
            "value": "meta/llama-3.1-70b",
            "search": "Llama 3.1 70B Meta llama3",
        },
    ],
    placeholder="Search models...",
)
```

**Gotchas summary for dcc.Dropdown search:**

1. **Component labels break search.** When `label` is an `html.Span` or any Dash component, search only matches against `value` unless you explicitly set the `search` property on each option. This is the single biggest gotcha.
2. **`search` is additive.** The `search` string is matched *in addition to* `value`, not instead of it. So include any aliases or alternate spellings in `search`.
3. **Performance with large option lists.** Above ~10,000 options the dropdown becomes sluggish. For very large lists, consider a callback-driven approach that filters options server-side based on `search_value`:

```python
@callback(
    Output("large-dropdown", "options"),
    Input("large-dropdown", "search_value"),
)
def filter_options(search):
    if not search:
        return all_options[:100]  # Show first 100 by default
    search_lower = search.lower()
    return [o for o in all_options if search_lower in o["label"].lower()][:100]
```

4. **`multi=True`** works with search -- selected items appear as tags, and the search box remains active for adding more.

## Summary of Recommendations

| Pattern | Best Component | Why |
|---|---|---|
| Collapsible options (top) | `dbc.Accordion` + `AccordionItem` | Built-in toggle header, `start_collapsed`, `always_open`, styled |
| Collapsible diagnostics (bottom) | `html.Details` + `html.Summary` | Zero callbacks, lightweight, semantic HTML5 |
| Dynamic filter rows | Pattern-matching callbacks + `Patch()` | Dict IDs with `ALL`/`MATCH`, partial updates via `Patch` |
| Copy to clipboard | `dcc.Clipboard` with `target_id` | No callback needed for simple cases; `content` prop for computed text |
| Toast notifications | `dbc.Toast` with `duration` | Auto-dismiss, `icon` for color coding, fixed positioning |
| Searchable dropdown | `dcc.Dropdown` with `search` option key | Always set `search` when using component labels |
