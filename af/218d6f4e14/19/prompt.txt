## Agent Definitions and Task Specifications

### Agent 1: **SRAgent Codebase Analyst**

**Role:** Systematic reverse-engineering of the SRAgent repository to produce a complete technical understanding.

**Instructions:**

1. **Repository Discovery Phase**
   - Locate the SRAgent repository. Begin by listing the full directory tree (all files, all depths).
   - Identify the primary language(s), framework(s), dependency manifest(s) (requirements.txt, pyproject.toml, package.json, etc.).
   - Read the README, any CONTRIBUTING, ARCHITECTURE, or design docs present in the repo.
   - Catalog every source file, configuration file, prompt template, and data file.

2. **Architectural Overview** → Output: `full_codebase_overview.md`
   - Describe the overall system architecture: what are the top-level components and how do they relate?
   - Identify the **entry points** (main scripts, CLI interfaces, API endpoints).
   - Map the **module dependency graph**: which modules import which, what are the layers of abstraction?
   - Describe the **configuration system**: how is the agent configured? Environment variables, YAML/JSON configs, command-line arguments, hardcoded defaults?
   - Identify all **external service integrations**: LLM API calls, database connections, file system I/O, web APIs, tool use.
   - Document the **error handling strategy**: how are failures caught, retried, logged, escalated?
   - Note the **testing approach**: unit tests, integration tests, evaluation harnesses.

3. **Control Flow and Data Flow Analysis** → Output: `flow_diagrams.md`
   - Trace the **end-to-end execution flow** from input (what triggers the agent?) to output (what does it produce?). Document every step.
   - Identify all **decision points** where the agent branches based on LLM output, tool results, or configuration.
   - Map the **data flow**: what data enters the system, how is it transformed at each stage, what intermediate representations exist, what is the final output?
   - Document any **feedback loops**: does the agent iterate, retry, self-correct, or refine its outputs?
   - Identify **state management**: what state is maintained across steps? How is it stored (in-memory, files, database)?

4. **Prompt Engineering and Context Management** → Output: `prompt_and_context_management.md`
   - Extract and catalog **every prompt template** or system message in the codebase. For each:
     - Where is it defined (file, line)?
     - What variables/placeholders does it contain?
     - What role does it serve in the overall flow?
     - How is it assembled at runtime (string formatting, template engine, dynamic construction)?
   - Analyze **context window management**:
     - How does the agent manage token limits?
     - Is there summarization, truncation, sliding window, or prioritized context selection?
     - How is conversation history maintained and pruned?
   - Document **prompt chaining**: how does output from one LLM call feed into the next?
   - Identify any **few-shot examples**, **chain-of-thought** elicitation, or **structured output** enforcement (JSON mode, XML parsing, regex extraction).

5. **Sub-Agent Architecture** → Output: `subagent_architecture.md`
   - If SRAgent uses sub-agents, specialized workers, or a multi-agent topology:
     - How are sub-agents defined, instantiated, and orchestrated?
     - What is the communication protocol between agents (function calls, message queues, shared state)?
     - How is work divided and results aggregated?
     - Is there a supervisor/worker pattern, a pipeline, a DAG, or something else?
   - If SRAgent is monolithic, document how responsibilities are separated within the single agent and whether the architecture could benefit from decomposition.

6. **Reusable Patterns** → Output: `reusable_patterns.md`
   - Extract **design patterns** that are generalizable beyond SRAgent. For each pattern:
     - **Name** it descriptively.
     - **Describe** the pattern in abstract terms.
     - **Show** a concrete code example from SRAgent.
     - **Assess** applicability: in what other agentic systems would this pattern be useful?
   - Specifically look for patterns in:
     - Tool use and tool result parsing
     - LLM output validation and structured extraction
     - Retry and self-healing logic
     - Dynamic prompt construction
     - Agent orchestration and delegation
     - Logging, observability, and debugging support
     - Configuration and extensibility

7. **Code Organization Practices** → Output: `code_organization_practices.md`
   - Assess the **file and directory structure**: is it logical, navigable, and consistent?
   - Evaluate **naming conventions** for files, classes, functions, variables.
   - Document how **separation of concerns** is achieved (or not).
   - Note any use of **abstractions, interfaces, or base classes** that promote extensibility.
   - Identify **anti-patterns** or technical debt.

### Agent 2: **Paper Analyst**

**Role:** Read, summarize, and deeply analyze the research paper included in the SRAgent codebase.

**Instructions:**

1. **Locate the Paper**
   - Search the SRAgent repository for PDF, LaTeX, or markdown files that constitute the research paper.
   - If multiple documents exist, identify the primary publication.

2. **Structured Summary** → Output: `paper_summary_and_findings.md`
   - Provide a structured summary covering:
     - **Problem statement**: What problem does SRAgent address? Why does it matter?
     - **Proposed approach**: What is the core method/system? Describe the architecture and workflow as presented in the paper.
     - **Key contributions**: What does the paper claim as novel?
     - **Experimental setup**: What benchmarks, datasets, baselines, and metrics are used?
     - **Main results**: What are the headline numbers? How does SRAgent compare to baselines?
     - **Ablation studies**: What components are tested in isolation? What do ablations reveal about what matters?
     - **Limitations acknowledged**: What do the authors themselves identify as limitations?

3. **Methodology Deep Dive** → Output: `methodology_deep_dive.md`
   - Go beyond the summary to analyze the methodology in detail:
     - How does the agentic loop work step by step?
     - What LLM(s) are used, and how are they configured (temperature, max tokens, model version)?
     - What tools does the agent have access to, and how does it decide which to use?
     - How is the agent evaluated? Are the evaluation metrics appropriate for the claims?
     - What is the computational cost (tokens, API calls, time, money)?
     - How reproducible is the work? Is enough detail provided to reimplement?

### Agent 3: **Paper Critic** (Subagent)

**Role:** Adversarial reviewer identifying gaps, weaknesses, and unaddressed issues in the paper.

**Instructions:**

Produce → `paper_critique.md`

Evaluate the paper across these dimensions, being thorough and specific:

1. **Methodological Gaps**
   - Are there confounding variables in the evaluation?
   - Is the comparison to baselines fair (same compute budget, same information access)?
   - Are there selection biases in the benchmark tasks?
   - Does the method generalize beyond the tested domain?

2. **Evaluation Weaknesses**
   - Are the metrics sufficient to capture real-world utility?
   - Is statistical significance reported? Variance across runs?
   - Are there ceiling/floor effects in the benchmarks?
   - How would the system perform on adversarial or out-of-distribution inputs?

3. **Unaddressed Questions**
   - What failure modes are not analyzed?
   - What is the cost-effectiveness compared to simpler approaches?
   - How does performance degrade with weaker/cheaper models?
   - What about safety, alignment, or unintended behaviors of the agent?
   - Is there analysis of when the agent knows it doesn't know (calibration)?

4. **Missing Comparisons**
   - What recent related work is not compared against?
   - Are there obvious alternative approaches that should have been tried?

5. **Reproducibility Concerns**
   - Can the results be reproduced from the paper alone?
   - Are prompts, hyperparameters, and random seeds fully specified?
   - Is the code release complete enough to verify claims?

6. **Strength Acknowledgment**
   - Despite the critique, what does the paper do genuinely well?
   - What aspects of the approach are most promising for future work?

## Quality Standards

All outputs must meet these standards:

1. **Specificity over generality**: Every claim must reference specific files, functions, line numbers, paper sections, or code snippets. "The agent uses good prompt engineering" is not acceptable. "The agent constructs prompts in `src/prompts/builder.py:L45-L89` using a template registry pattern where system messages are loaded from YAML files in `config/prompts/` and dynamically populated with task-specific context via f-string interpolation" is acceptable.

2. **Evidence-based assessment**: Opinions must be grounded in observable evidence from the codebase or paper. If making a judgment ("this pattern is better than that one"), justify it with specific technical reasoning.

3. **Actionability**: Findings should be phrased as actionable insights wherever possible. Not just "X is a weakness" but "X is a weakness; it could be addressed by Y, as demonstrated by Z."

4. **Completeness signals**: Each output document must end with a "Completeness Assessment" section stating: (a) what was fully covered, (b) what was partially covered and why, (c) what was not covered and why.

5. **Cross-referencing**: Outputs should reference other outputs in the research directory where relevant (e.g., "As identified in `01_sragent_codebase_analysis/reusable_patterns.md`, the retry pattern used in SRAgent addresses the reliability concern raised in `02_paper_analysis/paper_critique.md`").

## Constraints and Reminders

- **Do not hallucinate code or paper content.** If you cannot access a file, say so explicitly and note it as a gap.
- **Read before writing.** Always read the actual source files before making claims about them. Do not guess at file contents based on names.
- **Preserve nuance.** If something is genuinely ambiguous or could be interpreted multiple ways, present the alternatives rather than forcing a single interpretation.
- **Be honest about limitations.** If the analysis is incomplete due to access constraints, time, or complexity, state this clearly rather than papering over gaps.
- **Think step by step.** For complex analyses (especially control flow tracing and prompt management), work through the logic methodically rather than jumping to conclusions.
- **Write for a technical audience.** Assume the reader is an experienced software engineer familiar with LLM-based agentic systems. Do not over-explain basic concepts, but do explain domain-specific or project-specific details.
