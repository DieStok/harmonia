# Implementation Spec: Uniform Experiment Tracking with Unique Run ID

**Date:** 11 February 2026
**Status:** Draft — awaiting user review
**Depends on:** Failure mode taxonomy (`docs/processes/11_02_2026_interpreting_logs_and_traces.md`)

---

## 1. Problem Statement

Currently, logs and results folders cannot be reliably linked:
- Logs: `logs/{DD-MM-YYYY_HHMM}_{experiment_name}_{SLURM_JOB_ID}.out`
- Results: `results/{experiment_name}_{YYYYMMDD_HHMMSS}/`
- Manual logs: `logs/beaker_{YYYYMMDD_HHMMSS}.log`, `logs/ollama_{YYYYMMDD_HHMMSS}.log`

The connection relies on matching experiment names and approximate timestamps, which is fragile — especially when `run_experiment.py` retries create multiple results folders per job (itself a bug to be fixed).

---

## 2. Solution: Unique Run ID

### 2.1 The Run ID

Each experiment invocation gets a unique **run_id**: an 8-character lowercase hex string (e.g., `a3f7b2c1`).

- Generated by: `exec_apptainer_harmonia.sh` (the common entry point for both manual and automated experiments)
- Generation method: `python3 -c "import secrets; print(secrets.token_hex(4))"` or `head -c 4 /dev/urandom | xxd -p`
- Passed to: log filenames, results folder name, `.experiment_id` metadata file, and downstream scripts

### 2.2 Naming Conventions (After Implementation)

**Automated experiments (SBATCH):**
```
logs/{DD-MM-YYYY_HHMM}_{experiment_name}_{SLURM_JOB_ID}_{run_id}.out
logs/{DD-MM-YYYY_HHMM}_{experiment_name}_{SLURM_JOB_ID}_{run_id}.err
logs/{experiment_name}_{SLURM_JOB_ID}_{run_id}_beaker.log
logs/{experiment_name}_{SLURM_JOB_ID}_{run_id}_ollama.log
results/{experiment_name}_{YYYYMMDD_HHMMSS}_{run_id}/
```

**Manual experiments:**
```
logs/{experiment_name}_{run_id}_beaker.log
logs/{experiment_name}_{run_id}_ollama.log
results/{experiment_name}_{YYYYMMDD_HHMMSS}_{run_id}/
```

### 2.3 Metadata File: `.experiment_id`

Created inside each results folder at experiment start time.

## 3. Files to Modify

### 3.1 `exec_apptainer_harmonia.sh`

**Changes:**
1. Generate `RUN_ID` at the top (after argument parsing):
   ```bash
   RUN_ID=$(python3 -c "import secrets; print(secrets.token_hex(4))")
   ```
2. Incorporate `RUN_ID` into results folder naming:
   ```bash
   RESULTS_DIR="${DEFAULT_RESULTS_DIR}/${EXPERIMENT_NAME}_${TIMESTAMP}_${RUN_ID}"
   ```
3. Incorporate `RUN_ID` into `JOB_NAME` (used for log file naming):
   ```bash
   JOB_NAME="${EXPERIMENT_NAME}_${SLURM_JOB_ID:-manual}_${RUN_ID}"
   ```
4. Write `.experiment_id` JSON file into results directory after creating it.
5. Export `RUN_ID` as environment variable for downstream scripts.

### 3.2 `sbatch_template_gpu.sh` and `sbatch_template.sh`

**Changes:**
1. Accept `RUN_ID` from `exec_apptainer_harmonia.sh` (it's already passed via `--job-name`).
2. Incorporate `RUN_ID` into the `exec >` redirect filenames:
   ```bash
   LOG_OUT="logs/${LOG_TIMESTAMP}_{{experiment_name}}_${SLURM_JOB_ID}_${RUN_ID}.out"
   ```
3. **Important:** The `RUN_ID` needs to be generated in the SBATCH script (since it runs before `exec_apptainer_harmonia.sh`) and passed to exec via `--job-name` or a new `--run-id` flag.

   Actually, the flow is: SBATCH script -> calls `exec_apptainer_harmonia.sh`. So the SBATCH template should generate the `RUN_ID` and pass it down:
   ```bash
   RUN_ID=$(python3 -c "import secrets; print(secrets.token_hex(4))")
   LOG_OUT="logs/${LOG_TIMESTAMP}_{{experiment_name}}_${SLURM_JOB_ID}_${RUN_ID}.out"
   ...
   ./exec_apptainer_harmonia.sh --run-id "$RUN_ID" --config ... --job-name ...
   ```

### 3.3 `exec_apptainer_harmonia.sh` — New `--run-id` flag

Add a `--run-id` argument:
```bash
--run-id|-R)
    RUN_ID="$2"
    shift 2
    ;;
```
If not provided (manual mode), generate one automatically.

### 3.4 `run_experiment.py`

**Changes:**
1. **Enforce single run per invocation.** Remove retry logic that creates new results folders. If the experiment fails, exit with non-zero status. Let SLURM `--array` or the user handle retries.
2. Read `RUN_ID` from the environment variable or the `.experiment_id` file.
3. Do not create additional results folders.

### 3.5 `generate_jobs.py`

**No changes needed.** The `RUN_ID` is generated at runtime by the SBATCH script, not at job generation time.

## 4. CLI Log Analysis Tool

### 4.1 File: `code_development_tools_agents/monitoring_and_evaluation/read_and_analyze_logs_and_traces_cli.py`

**Core features:**
- Analyze newest N runs (default: 10) from logs folder
- Cross-reference logs with trace.json using `run_id` (new) or experiment name + timestamp matching (legacy fallback)
- Categorize errors using YAML taxonomy
- Output human-readable report (default) or JSON (`--json`)

**Command-line interface:**
```
python read_and_analyze_logs_and_traces_cli.py [OPTIONS]

Options:
  -n, --num-runs N        Number of most recent runs to analyze (default: 10)
  -l, --log-dir DIR       Log directory (default: see GLOBAL_VARIABLES)
  -r, --results-dir DIR   Results directory (default: see GLOBAL_VARIABLES)
  -t, --taxonomy FILE     Error taxonomy YAML (default: types_of_log_and_trace_problems.yaml)
  --mode {auto,manual,all} Filter by experiment mode (default: all)
  --json                  Output JSON instead of human-readable text
  --verbose               Show detailed trace analysis per turn
  --run-id ID             Analyze a specific run by ID
  --experiment NAME       Filter by experiment name pattern
  -h, --help              Show help message
```

**Global variables (editable at top of script):**
```python
# === GLOBAL VARIABLES — edit these if naming conventions change ===
```

### 4.2 Pydantic Output Schema

```python
from pydantic import BaseModel
from typing import Optional
from enum import Enum

class SchemaVersion(str, Enum):
    V1 = "1.0"

class ExperimentMode(str, Enum):
    AUTOMATED = "automated"
    MANUAL = "manual"

class Severity(str, Enum):
    CRITICAL = "critical"    # Experiment cannot run at all
    ERROR = "error"          # Experiment ran but failed to produce output
    WARNING = "warning"      # Experiment ran but with degraded quality
    INFO = "info"            # Non-fatal observations

class DetectedProblem(BaseModel):
    problem_id: str              # e.g., "1A_beaker_server_hung"
    category: str                # e.g., "infrastructure"
    name: str                    # e.g., "Beaker Server Hung"
    severity: Severity
    evidence: str                # The matching text/pattern that triggered detection
    remediation: list[str]       # Suggested fixes

class TurnAnalysis(BaseModel):
    turn: int
    response_type: str           # "llm_response", "timeout", "error"
    duration_seconds: float
    has_tool_calls: bool
    raw_message_count: int
    problems: list[DetectedProblem]

class RunAnalysis(BaseModel):
    run_id: Optional[str]        # 8-char hex, None for legacy runs
    experiment_name: str
    mode: ExperimentMode
    slurm_job_id: Optional[int]
    timestamp: str
    llm_provider: Optional[str]
    llm_model: Optional[str]
    log_file: Optional[str]      # Path to .out file
    results_folder: Optional[str] # Path to results dir
    has_trace: bool
    has_metrics: bool
    total_turns: int
    successful_turns: int
    timed_out_turns: int
    total_duration_seconds: Optional[float]
    problems: list[DetectedProblem]
    turns: Optional[list[TurnAnalysis]]  # Only populated with --verbose

class AnalysisReport(BaseModel):
    schema_version: SchemaVersion
    generated_at: str            # ISO timestamp
    log_dir: str
    results_dir: str
    taxonomy_file: str
    num_runs_analyzed: int
    runs: list[RunAnalysis]
    summary: dict                # Aggregated problem counts by category
```

### 4.3 Linkage Logic

**New-style (with run_id):**
1. Parse log filename to extract `run_id`
2. Find results folder containing `run_id` in its name
3. Verify match by reading `.experiment_id` file

**Legacy fallback (without run_id):**
1. Parse log filename to extract `experiment_name` and `SLURM_JOB_ID`
2. Find results folders matching `experiment_name`
3. Filter by timestamp proximity (within the job's time window from the log)
4. If multiple matches, flag as anomaly (Category: "multiple_results_per_job")

**Manual mode:**
1. Parse Beaker log filename to extract `experiment_name` and optionally `run_id`
2. Match to results folder by `run_id` or `experiment_name` + timestamp

```yaml
      source: "log|trace|both"
      snippet: |

      - "Second suggested fix"
      - "Third suggested fix"
```

## 6. Implementation Order

1. **YAML taxonomy** — write `types_of_log_and_trace_problems.yaml` with all 13 problem classes from the failure mode documentation
2. **Pydantic schema** — define output models in the CLI tool
3. **CLI tool core** — implement log discovery, trace loading, problem detection, report generation
4. **`exec_apptainer_harmonia.sh` changes** — add `--run-id` flag, `RUN_ID` generation, `.experiment_id` file
5. **SBATCH template changes** — generate `RUN_ID`, pass to exec, use in log filenames
6. **`run_experiment.py` changes** — enforce single run, remove retry-with-new-folder logic
7. **Test with existing logs** — verify the CLI tool works on legacy (no run_id) log/trace data
8. **Relaunch experiments** — test new naming with a subset of experiments

## 7. Open Questions

1. **RUN_ID generation location:** The SBATCH template generates `RUN_ID` before calling `exec_apptainer_harmonia.sh`. For manual mode, `exec_apptainer_harmonia.sh` generates it. Is this dual-source acceptable, or should we always have `exec_apptainer_harmonia.sh` generate it and somehow feed it back to the SBATCH log redirect? (Possible via a temp file approach, but adds complexity.)
Answer: dual-source is acceptable if documented well. 

1. **`run_experiment.py` retry behavior:** Should retries be removed entirely, or should the script retry within the same results folder (overwriting the previous trace.json)? If it retries and overwrites, we lose the evidence of the failed attempt.
Answer: don't retry, just fail so I can diagnose.

2. **Legacy log handling:** The spec says we won't handle older log formats, but the CLI tool should still work on the current batch of logs (10 Feb 2026) that don't have `run_id`. The fallback matching by experiment name + timestamp handles this. Confirm this is sufficient.
Answer: this is sufficient.

## 8. Non-Goals

- The CLI tool does NOT fix errors — it only diagnoses and reports
- The CLI tool does NOT submit new SLURM jobs
- The CLI tool does NOT modify log or trace files
- No web UI — this is strictly a command-line tool for agents and humans
